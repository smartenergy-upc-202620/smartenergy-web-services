# Sprint 1

Goal: a first working version of the SmartEnergy backend, reachable through the API Gateway and documented with Swagger, automated tests, BDD specifications and a Postman collection.

## Status at a glance

| Implemented | Not implemented (future sprints) |
| --- | --- |

| Alert Service (rules, evaluation, alerts) | Physical sensors |

## Delivered

### Identity & Access (`user-service`, port 3001)

| Endpoint | Use case | Result |
| --- | --- | --- |
| `POST /api/v1/auth/register` | `RegisterUserUseCase` | Creates a user with a bcrypt-hashed password and the role `HOME_USER` (default) or `BUSINESS_ADMIN`. 409 if the email exists. |
| `POST /api/v1/auth/login` | `LoginUserUseCase` | Returns `{ accessToken, user }`. 401 for wrong credentials. |
| `GET /api/v1/users/me` | `GetCurrentUserUseCase` | Profile of the bearer of the token. 401 without a valid token. |

The password and its hash are never returned. Emails are normalized (trimmed, lower case) by the `Email` value object.

### Energy Monitoring (`energy-monitoring-service`, port 3002)

| Endpoint | Use case | Result |
| --- | --- | --- |
| `POST /api/v1/measurements` | `CreateEnergyMeasurementUseCase` | Stores `deviceId`, `consumptionKwh` (≥ 0) and `measuredAt`. The id is generated by the backend. |
| `GET /api/v1/measurements?deviceId=` | `ListEnergyMeasurementsUseCase` | Most recent first, optional device filter. |
| `GET /api/v1/measurements/summary?deviceId=` | `GetEnergyConsumptionSummaryUseCase` | `{ totalMeasurements, totalConsumptionKwh, averageConsumptionKwh }`, rounded to 3 decimals. |
| `GET /api/v1/measurements/:id` | `GetEnergyMeasurementByIdUseCase` | 404 if not found, 400 if the id is not a UUID. |

`/summary` is declared before `/:id` in both the service and the gateway, so it is never captured as an id (covered by a test).

### Alerting (`alert-service`, port 3003)

| Endpoint | Use case | Result |
| --- | --- | --- |
| `POST /api/v1/alert-rules` | `CreateAlertRuleUseCase` | Rule `{ name, thresholdKwh > 0, active (default true) }`. |
| `GET /api/v1/alert-rules` | `ListAlertRulesUseCase` | Most recent first. |
| `POST /api/v1/alerts/evaluate` | `EvaluateMeasurementForAlertsUseCase` | Loads the active rules, evaluates `{ deviceId, consumptionKwh }` with the `ThresholdAlertStrategy`, stores one alert per exceeded rule and returns `{ evaluatedRules, alerts }`. |
| `GET /api/v1/alerts` | `ListAlertsUseCase` | Most recent first. |
| `GET /api/v1/alerts/:id` | `GetAlertByIdUseCase` | 404 if not found. |

An alert is raised when consumption is strictly greater than the threshold (8.2 kWh against 5 kWh raises an alert; 5 kWh does not).

In this sprint the evaluation is requested explicitly over REST. The event-driven integration with Energy Monitoring comes later.

### API Gateway (port 3000)

- Exposes the 12 routes above under `http://localhost:3000/api/v1` and forwards them to the owning service, preserving method, path, query string, body, `Authorization` header and status code.
- `GET /api/v1/system/health` reports the status of the three services.
- Contains no business logic or validation.

### Cross-cutting

- PostgreSQL with one schema per context (`identity_access`, `energy_monitoring`, `alerting`) and four tables: `users`, `energy_measurements`, `alert_rules`, `alerts`.
- Consistent errors: 400 (validation/domain rules), 401, 404, 409, 503 (gateway, service down) and a generic 500 without stack traces.
- Swagger on every application (`/docs`), including the gateway.
- Tests: 39 suites and 143 tests; see [`testing.md`](testing.md).
- BDD specifications in `features/` (22 scenarios tagged `@sprint-1`).
- Postman collection and local environment in `postman/`.
- Reproducible demo data via `pnpm demo:seed` (through the gateway).

## Validation performed

On Windows 11, Node 22.20, pnpm 12.5, Docker 28.5 (PostgreSQL 17):

- `pnpm install`, `pnpm build`, `pnpm test`, `pnpm test:cov` passed.
- `docker compose up -d` started PostgreSQL and its health check reported `healthy`.
- The four services started with `pnpm start:dev:all`. `/api/v1/health` and `/docs` answered 200 on ports 3000–3003.
- The full flow ran through the gateway: register, login, `/users/me`, create/list/get measurement, summary, create rule (5 kWh), evaluate 8.2 kWh (one alert generated), list alerts, get the alert.
- The Postman collection ran with Newman: 23 requests, 33 assertions, 0 failures.

## Not included (out of scope)

IoT Gateway, MQTT, Message Broker, Event Processor, Observer/event-driven integration, physical sensors, ML/prediction, recommendations, frontend, payments, subscriptions and cloud deployment.

## Open points for the next sprints

- **Authorization on measurements and alerts.** These endpoints are public and measurements are not linked to a user or device owner yet. Validating the JWT in these services (or at the gateway) needs a decision on how the token or its claims are shared between contexts.
- **Migrations.** Tables are created with TypeORM synchronization (development only, disabled in production). Versioned migrations are needed before any shared environment.
- **Scalability of the queries.** Lists have no pagination, and the consumption summary is computed in memory over the matching rows. Both are marked with `TODO` comments in the code.
- **Rule evaluation triggering.** `POST /alerts/evaluate` is explicit. It will be replaced or complemented by events from Energy Monitoring.
- The applications are not containerized; only PostgreSQL runs in Docker.
