# Deployment

How to deploy the SmartEnergy backend (Sprint 1) to a cloud provider that builds pnpm monorepos, with Railway as the reference. The same repository keeps working locally (see the README).

## Deployment architecture

Five Railway services in one project, all built from the same repository root:

```
                    Internet
                       │  https://<gateway-domain>/api/v1/...
                       ▼
               ┌───────────────┐
               │  api-gateway  │  public domain (entry point, Swagger /docs)
               └──────┬────────┘
     private network  │  USER_SERVICE_URL / ENERGY_SERVICE_URL / ALERT_SERVICE_URL
       ┌──────────────┼───────────────────────────┐
       ▼              ▼                           ▼
┌──────────────┐ ┌───────────────────────────┐ ┌───────────────┐
│ user-service │ │ energy-monitoring-service │ │ alert-service │
└──────┬───────┘ └────────────┬──────────────┘ └──────┬────────┘
       │ identity_access      │ energy_monitoring      │ alerting
       └──────────────────────┼────────────────────────┘
                              ▼
                    ┌───────────────────┐
                    │ PostgreSQL        │  one instance, one schema per context
                    └───────────────────┘
```

| Service | Source | Database schema | Needs |
| --- | --- | --- | --- |
| `api-gateway` | `apps/api-gateway` | none | the three service URLs |
| `user-service` | `apps/user-service` | `identity_access` | database, `JWT_SECRET` |
| `energy-monitoring-service` | `apps/energy-monitoring-service` | `energy_monitoring` | database |
| `alert-service` | `apps/alert-service` | `alerting` | database |
| PostgreSQL | Railway PostgreSQL template | all three schemas | — |

Each business service owns its schema and only migrates and queries that schema. The gateway never connects to the database.

## Commands

All commands run from the repository root (the pnpm workspace root). Do not set a per-app root directory: the apps share `package.json`, `pnpm-lock.yaml`, `libs/` and `tsconfig.json`.

| Service | Build command | Pre-deploy command (migrations) | Start command |
| --- | --- | --- | --- |
| api-gateway | `pnpm build:api-gateway` | — | `pnpm start:prod:api-gateway` |
| user-service | `pnpm build:user-service` | `pnpm migration:run:user` | `pnpm start:prod:user-service` |
| energy-monitoring-service | `pnpm build:energy-monitoring-service` | `pnpm migration:run:energy` | `pnpm start:prod:energy-monitoring-service` |
| alert-service | `pnpm build:alert-service` | `pnpm migration:run:alert` | `pnpm start:prod:alert-service` |

- The build output is one webpack bundle per app: `dist/apps/<app>/main.js`. `start:prod:<app>` runs `node dist/apps/<app>/main`.
- Dependencies are installed with `pnpm install --frozen-lockfile`. The required pnpm version is pinned in `package.json` (`packageManager: pnpm@12.5.1`), and the Node version must satisfy `engines` (`^20.19.0 || ^22.13.0 || >=24.11.0`, required by TypeORM).
- The build needs devDependencies (`@nestjs/cli`, webpack). pnpm 12 installs them even when `NODE_ENV=production`; if a builder installs production dependencies only, use `pnpm install --frozen-lockfile --prod=false && pnpm build:<app>` as build command.

## Database migrations

Tables are created and evolved only by versioned TypeORM migrations. Each Bounded Context has its own migration DataSource and migrations, in its infrastructure layer:

| Context | DataSource | Migrations | Creates |
| --- | --- | --- | --- |
| Identity & Access | `apps/user-service/src/infrastructure/persistence/typeorm/identity-access.data-source.ts` | `.../migrations/1791296250262-InitialIdentityAccessSchema.ts` | schema `identity_access`, table `users` (PK, unique `email`) |
| Energy Monitoring | `apps/energy-monitoring-service/src/infrastructure/persistence/typeorm/energy-monitoring.data-source.ts` | `.../migrations/1791296252925-InitialEnergyMonitoringSchema.ts` | schema `energy_monitoring`, table `energy_measurements` (PK, index on `device_id`) |
| Alerting | `apps/alert-service/src/infrastructure/persistence/typeorm/alerting.data-source.ts` | `.../migrations/1791296254937-InitialAlertingSchema.ts` | schema `alerting`, tables `alert_rules` and `alerts` (PKs, index and FK on `rule_id`) |

The initial migrations were generated by TypeORM from the ORM entities, so they match them exactly. After migrating a clean database, `migration:generate --check` reports no changes for the three contexts.

Scripts:

| Script | Purpose |
| --- | --- |
| `pnpm migration:run:user` / `:energy` / `:alert` | Creates the context schema if needed and applies its pending migrations (one transaction per migration). |
| `pnpm migration:run:all` | The three above, in order (local convenience). |
| `pnpm migration:revert:user` / `:energy` / `:alert` | Reverts the last applied migration of that context only. |
| `pnpm migration:generate:user <path>` (also `:energy`, `:alert`) | Generates a new migration from the differences between the ORM entities and the database, e.g. `pnpm migration:generate:alert apps/alert-service/src/infrastructure/persistence/typeorm/migrations/AddRuleType`. Register the new class in the context DataSource (`migrations: [...]`); a test fails if a migration file is not registered. |

Notes:

- Each context keeps its migration history in `<schema>.migrations`, so contexts never share migration state.
- Reverting the initial migration drops the context tables but keeps the schema (it holds the migrations table).
- Migration scripts read the same variables as the apps (`DATABASE_URL` or `POSTGRES_*`, `DB_SSL`) and load `.env` if present. They run TypeScript through `ts-node` + `tsconfig-paths`, which are production dependencies for that reason.
- `synchronize` is never used in production: `NODE_ENV=production` forces it off. Outside production it is opt-in (`DB_SYNCHRONIZE=true`) and must not be mixed with migrations on the same database.

## Environment variables

Placeholders are documented in [`.env.example`](../.env.example). Never commit real values; in Railway set them as service variables (secrets are masked).

| Variable | gateway | user | energy | alert | Notes |
| --- | :-: | :-: | :-: | :-: | --- |
| `NODE_ENV` | ✓ | ✓ | ✓ | ✓ | `production` in the cloud. Disables synchronize, removes localhost fallbacks and makes missing configuration fail at startup. |
| `PORT` | ✓ | ✓ | ✓ | ✓ | Injected by Railway. Takes precedence over `API_GATEWAY_PORT` / `USER_SERVICE_PORT` / `ENERGY_MONITORING_SERVICE_PORT` / `ALERT_SERVICE_PORT` (local defaults 3000–3003). |
| `DATABASE_URL` | | ✓ | ✓ | ✓ | Preferred in the cloud, e.g. `${{Postgres.DATABASE_URL}}`. Takes precedence over `POSTGRES_*`. |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | | ✓ | ✓ | ✓ | Alternative to `DATABASE_URL`. In production all but the port are required. |
| `DB_SSL` | | ✓ | ✓ | ✓ | `true` enables TLS. If unset, the URL decides (`?sslmode=require`). |
| `DB_SSL_REJECT_UNAUTHORIZED` | | ✓ | ✓ | ✓ | `false` accepts self-signed certificates. Default `true`. |
| `DB_SYNCHRONIZE` | | ✓ | ✓ | ✓ | Leave unset in the cloud (ignored in production anyway). |
| `JWT_SECRET` | | ✓ | | | Required. Long random value (`node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`). |
| `JWT_EXPIRES_IN` | | ✓ | | | Default `1h`. |
| `USER_SERVICE_URL`, `ENERGY_SERVICE_URL`, `ALERT_SERVICE_URL` | ✓ | | | | Required in production (no localhost fallback). |

Startup fails fast with an explicit message when, in production, the database is not configured (`Database is not configured: set DATABASE_URL or ...`) or a gateway URL is missing (`ALERT_SERVICE_URL must be set in production`). Error messages never include the connection string.

## Health checks and Swagger

- Every app exposes `GET /api/v1/health` (200 with `{ status: "ok", service, timestamp }`). Use it as the provider health check path. It reports that the process is up; it does not query the database.
- The gateway also exposes `GET /api/v1/system/health`: 200 when the three services answer their health check, 503 otherwise. It is useful for monitoring, but do not use it as the gateway's deploy health check: a downstream outage would block gateway deploys.
- Swagger UI is available at `/docs` (and the OpenAPI JSON at `/docs-json`) on all four apps, including in production, for this academic deployment.

## Railway procedure

1. **Project and database.** Create a Railway project and add a PostgreSQL database (Railway template). It exposes `DATABASE_URL` (private network) and `DATABASE_PUBLIC_URL`.
2. **Four services from the repository.** Add four services from the same GitHub repository and branch. For each one:
   - Root directory: repository root (leave empty).
   - Build command, pre-deploy command and start command: see [Commands](#commands).
   - Health check path: `/api/v1/health`.
   - Watch paths (optional, avoids redeploying every service on each push): `apps/<app>/**`, `libs/**`, `package.json`, `pnpm-lock.yaml`.
3. **Variables of the business services** (`user-service`, `energy-monitoring-service`, `alert-service`):
   - `NODE_ENV=production`
   - `DATABASE_URL=${{Postgres.DATABASE_URL}}` (reference variable; adjust `Postgres` to the database service name).
   - `DB_SSL`: not needed on the private network. If you connect through `DATABASE_PUBLIC_URL` and TLS is required, set `DB_SSL=true` (and `DB_SSL_REJECT_UNAUTHORIZED=false` only if the certificate is self-signed).
   - `PORT`: fix it (`3001`, `3002`, `3003`) so that the private URLs used by the gateway are stable.
   - user-service only: `JWT_SECRET` (secret) and `JWT_EXPIRES_IN=1h`.
4. **Variables of the gateway:**
   - `NODE_ENV=production`
   - `USER_SERVICE_URL=http://${{user-service.RAILWAY_PRIVATE_DOMAIN}}:3001`
   - `ENERGY_SERVICE_URL=http://${{energy-monitoring-service.RAILWAY_PRIVATE_DOMAIN}}:3002`
   - `ALERT_SERVICE_URL=http://${{alert-service.RAILWAY_PRIVATE_DOMAIN}}:3003`

   (Service names must match the Railway service names. Public `https://...up.railway.app` URLs also work, at the cost of leaving the private network.) The apps listen on all interfaces (IPv4 and IPv6), which Railway private networking needs.
5. **Public domains.** Generate a public domain for the gateway (client entry point). For this academic deployment also generate one for each business service so that their Swagger is reachable; otherwise they can stay private.
6. **Deploy order.** Deploy PostgreSQL, then the three business services (their pre-deploy commands create the schemas and tables), then the gateway.
7. **Smoke test** against `https://<gateway-domain>`:
   - `GET /api/v1/health` and `GET /api/v1/system/health` → 200
   - `/docs` on the four domains
   - Sprint 1 flow with the Postman collection, setting `gatewayUrl` (and the direct service URLs) to the deployed domains, or `GATEWAY_URL=https://<gateway-domain> pnpm demo:seed` from a local machine (demo data; never against a database with real users).

## Rollback

- **Application.** Redeploy the previous successful deployment of the affected service from the Railway deployments list. Services are deployed independently, so roll back only the one that failed.
- **Failed migration.** Migrations run one transaction per migration: a failing migration is rolled back by PostgreSQL and the pre-deploy step fails, so the new version is not started and the previous one keeps running.
- **Undoing an applied migration.** If a release must be rolled back together with a migration it introduced, run `pnpm migration:revert:<context>` (for example from a one-off Railway shell or locally with `DATABASE_URL` pointing to the database) once per migration to undo, before or after redeploying the previous version. `down` migrations can drop data: take a database backup first.
- Never revert the initial migrations on a database with data unless the goal is to delete it.

## Local vs. production

| Aspect | Local (`NODE_ENV=development`) | Production (`NODE_ENV=production`) |
| --- | --- | --- |
| Port | `API_GATEWAY_PORT` … `ALERT_SERVICE_PORT`, defaults 3000–3003 | `PORT` injected by the provider |
| Database | `docker compose` PostgreSQL, `POSTGRES_*` with localhost defaults | `DATABASE_URL` (or full `POSTGRES_*`), no defaults |
| SSL | off | `DB_SSL` / URL `sslmode` if the provider requires it |
| Tables | `pnpm migration:run:all` (or opt-in `DB_SYNCHRONIZE=true` on a throwaway database) | pre-deploy `migration:run:<context>`; synchronize always off |
| Gateway URLs | localhost defaults | required variables |
| Configuration source | `.env` | provider variables (no `.env`) |
| Swagger | `/docs` | `/docs` |
| Process | `pnpm start:dev:all` (watch) or `pnpm start:prod` (all four) | one service per app, `pnpm start:prod:<app>` |

### Local databases created in Sprint 1

Sprint 1 created the local tables with `synchronize`. Those tables have no migration history, so `migration:run` would fail on them ("relation already exists"). Recreate the local database before switching to migrations (this deletes local data):

```bash
docker compose down -v
docker compose up -d
pnpm migration:run:all
```

## Pending before production use

- Only `/users/me` is authenticated; measurement and alert endpoints are public.
- `/api/v1/health` does not check database connectivity.
- No pagination; the consumption summary is computed in memory.
- Swagger is public on purpose for the academic deployment; disable or protect it for a real production system.
